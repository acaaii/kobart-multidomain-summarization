# KoBART 다중 도메인(뉴스/사설/법률) 한국어 요약 모델

`digit82/kobart-summarization`을 뉴스·사설·법률 3개 도메인에 대해 파인튜닝하면서, 데이터 규모를 키워갈수록 특정 도메인(법률)의 생성 요약이 점점 장황해지는 현상을 발견하고, 그 원인을 4갈래로 나누어 진단한 뒤 통제 실험으로 검증까지 마친 프로젝트입니다.

핵심은 최종 성능 숫자보다 **"왜 이런 현상이 나타났는가"를 가설 → 검증 → 재실험으로 추적한 과정** 그 자체입니다.

## 요약

- 데이터: AI Hub 문서요약 텍스트 데이터셋 (뉴스 243,604건 / 사설 53,382건 / 법률 24,099건, train 기준)
- 모델: `digit82/kobart-summarization` (KoBART 기반 요약 모델) 파인튜닝
- 평가: ROUGE-1/2/L (Mecab/Kiwi 형태소 기반), BERTScore(`klue/roberta-large`), NLI 기반 사실 부합도(`Huffon/klue-roberta-base-nli`)
- 3단계 실험: 베이스라인 스케일업 → 4갈래 원인 진단 → 스텝 고정 재검증

## 데이터 및 전처리 (`preprocess.py`)

AI Hub 문서요약 텍스트 데이터셋(JSON)에서 뉴스/사설/법률 3개 도메인의 원문·추상 요약을 추출해 정제합니다.

- 도메인별 정제 규칙을 다르게 적용: 뉴스는 `[서울=뉴시스]` 류의 바이라인과 "OOO 기자 =" 패턴을 정규식으로 제거하지만, 법률 문서는 장식 기호(■▼▶★⊙)만 제거하고 판례 번호·법률 구두점은 그대로 보존
- 본문 50자 미만, 요약 10자 미만인 데이터와 중복 원문을 제외
- 최종 정제 데이터: 뉴스 243,604 / 사설 53,382 / 법률 24,099건 (train)

## 1단계 — 베이스라인 스케일업 실험 (`train.py`, `evaluate_a.py`)

도메인당 학습 샘플 수를 15k → 30k → 60k → 90k → 320k로 늘려가며 `num_train_epochs=3` 고정으로 반복 학습했습니다. 데이터가 늘수록 (에폭이 고정이므로) 총 학습 스텝 수도 함께 늘어나는데, 이 과정에서 특히 **법률 도메인 요약이 점점 장황해지고 문장이 자연스럽게 끝나지 않는 현상**이 관찰되었습니다. 이 증상이 이후 모든 진단 작업의 출발점이 되었습니다.

`train.py`에는 이 반복 실험 과정에서 남은 흔적이 그대로 있습니다. 예를 들어 `generation_max_length=64`로 설정하고 주석에 "과도한 문장 늘어짐 방지"라고 적어둔 부분은, 실은 최적 값이 아니라 **평가 시점의 임시방편**이었고, 오히려 이 값 때문에 학습 중 best-epoch 선택 자체가 왜곡되는 부작용이 있었다는 것을 3단계 재실험에서야 알게 됩니다(아래 참고).

## 2단계 — 네 갈래 원인 진단

"왜 법률 요약만 장황해지는가"를 하나의 원인으로 단정하지 않고, 가능한 설명을 각각 독립적으로 검증했습니다.

### 진단 1. 원본 데이터 자체가 도메인별로 요약 길이가 다르다 (`analyze_raw_length_full.py`)

토큰화 시 `truncation=True`로 이미 잘린 데이터로는 "원래 얼마나 길었는지" 알 수 없기 때문에, 정제된 CSV 원문을 `truncation=False`로 다시 토큰화해 실제 분포를 측정했습니다.

| 도메인 | 요약 길이 평균 | 중앙값 | 95th %ile | 최대 |
|---|---|---|---|---|
| news | 54.5 | 53 | 83 | 313 |
| editorial | 49.6 | 48 | 75 | 193 |
| **law** | **88.3** | **83** | **154** | **481** |

법률 도메인의 요약은 원본 자체가 뉴스/사설보다 구조적으로 1.6~1.8배 길다는 것이 확인되었습니다. 그런데 당시 토크나이징(`tokenize_data.py`)은 모든 도메인에 동일하게 `MAX_TARGET_LENGTH=128`을 적용하고 있었습니다. 실제로 토큰화된(잘린) 데이터에서 법률 요약의 95th %ile과 최댓값이 정확히 128에서 막혀 있는 것도 확인했습니다(`length_hist_stats.csv`) — **법률 요약이 대량으로 truncation되고 있었다는 뜻**입니다.

### 진단 2. 생성 단계에서도 강제로 캡(cap)에 걸리고 있는가 (`check_generation_cap_ratio.py`)

학습 데이터가 잘려서 들어갔다면, 생성 시점에도 모델이 `max_length`까지 억지로 문장을 채우고 EOS 토큰 없이 강제 종료될 가능성이 있습니다. 생성된 각 시퀀스에 `tokenizer.eos_token_id`가 포함되어 있는지 직접 검사했습니다.

| 도메인 | 강제 캡 비율 | 자연 종료 비율 | 평균 길이(raw) |
|---|---|---|---|
| news | 1.0% | 99.0% | 90.4 |
| editorial | 1.0% | 99.0% | 94.0 |
| **law** | **36.3%** | 63.7% | 127.9 |

법률 도메인만 생성의 1/3 이상이 EOS 없이 `max_length=128`까지 강제로 채워지고 있음을 확인 — 진단 1(구조적으로 긴 요약을 128로 잘라서 학습시킴)이 생성 단계까지 그대로 이어지고 있다는 직접적인 증거였습니다.

### 진단 3. 그럼 generation 파라미터만 조정해서 해결할 수 있는가 (`grid_search_generation.py`)

재학습 없이 `length_penalty`(0.6/0.8/1.0) × `num_beams`(2/4) × `no_repeat_ngram_size`(0/3) 총 12개 조합을 그리드서치했습니다. rougeL 기준 최적 조합(length_penalty=0.8, num_beams=4, no_repeat_ngram_size=3)에서도 `law_gen_len_mean`은 **123.05로 거의 고정**되어 있었고, length_penalty를 0.6~1.0으로 바꿔도 law만 유독 값이 전혀 움직이지 않았습니다. 즉 **생성 파라미터 튜닝만으로는 법률 도메인의 길이 문제를 해결할 수 없고, 학습 단계(토큰화 target length)를 고쳐야 한다**는 결론에 도달했습니다.

### 진단 4. 혹시 샘플링 자체가 편향된 것은 아닌가 (`analyze_sample_size_length.py`)

데이터량(N)을 5,000/10,000/20,000/30,000/전체로 바꿔가며 학습과 동일한 `shuffle(seed=42).select(range(N))` 방식으로 뽑은 요약 길이 평균이 N에 따라 달라지는지 확인했습니다. `merged_mean`은 62.39~64.08 사이에서만 움직여, 샘플링 방식 자체가 편향을 만드는 것은 아니라는 점(가설 기각)을 확인했습니다.

## 원인 수정: 법률 도메인만 target_length 재조정 (`tokenize_law_target190.py`)

진단 결과를 바탕으로, 법률 도메인만 `MAX_TARGET_LENGTH=190`으로 재토큰화했습니다(뉴스/사설은 128로도 충분해 재작업하지 않음). 이미 도메인별로 분리 저장된 `cleaned_dataset_{split}_law.csv`를 바로 읽어, 전체 데이터를 다시 분리하는 중복 작업 없이 처리했습니다.

## 3단계 — 스텝 수 고정 재검증 (`train_step_fixed_comparison.py`, `evaluate_step_fixed_comparison.py`)

1단계에서는 `num_train_epochs`를 고정한 채 데이터량을 늘렸기 때문에, "데이터량이 늘어서" 문제가 커진 것인지 "총 학습 스텝 수가 늘어서" 문제가 커진 것인지 구분할 수 없었습니다. 이를 분리하기 위해 **총 학습 스텝을 `max_steps=2800`으로 고정**한 채, 도메인당 학습 샘플 수만 5,000 → 10,000 → 20,000 → 24,000(법률 도메인의 실제 보유량 한계)으로 바꿔가며 재학습했습니다. 생성 설정도 그리드서치 결과를 반영해 `length_penalty=0.8, num_beams=4, no_repeat_ngram_size=3`으로 통일했습니다.

법률 도메인만 target_length=190으로 학습했으므로, 평가 시 법률 도메인의 생성 `max_length`는 128이 아닌 200으로 별도 설정해 재발을 방지했습니다.

평가는 도메인당 300건씩 총 900건에 대해 ROUGE + BERTScore + NLI 사실 부합도 + 생성 길이(gen_len_mean) + 강제 캡 비율을 종합 산출했습니다.

| 도메인당 샘플 수 | ROUGE-L | BERTScore | NLI 사실부합도 | gen_len_mean | 강제 캡 비율 | law ROUGE-L | law gen_len | law 캡 비율 |
|---|---|---|---|---|---|---|---|---|
| 5,000 | 31.73 | 70.89 | 16.06 | 67.24 | 8.0% | 26.74 | 93.22 | 24.0% |
| 10,000 | 32.70 | 71.52 | 17.36 | 76.75 | 14.6% | 28.12 | 104.68 | 40.0% |
| 20,000 | 32.01 | 71.36 | 18.03 | 78.87 | 17.6% | 27.76 | 105.63 | 45.7% |
| 24,000 | 32.18 | 71.69 | 17.01 | 78.38 | 16.3% | 27.58 | 102.97 | 41.3% |

**관찰 1 (가설 확인):** 총 스텝을 2,800으로 고정하자 `gen_len_mean`이 10,000건 지점 이후로 76~79 수준에서 **평평해집니다(saturate)**. 1단계에서는 데이터를 90k→320k로 늘릴 때마다 총 스텝도 비례해서 계속 늘어났고 그만큼 요약도 계속 길어지는 양상이었던 것과 대비됩니다. 즉 1단계에서 관찰된 "데이터를 늘릴수록 요약이 장황해진다"는 현상의 실제 원인은 데이터량 자체가 아니라 **그에 비례해서 함께 늘어난 총 학습 스텝(=학습을 오래 시킬수록 장황해짐)** 이었다는 가설이 지지되었습니다.

**관찰 2 (남은 한계, 숨기지 않음):** target_length를 190으로 늘리고 평가 `max_length`도 200으로 늘렸음에도, 법률 도메인의 강제 캡 비율은 여전히 24~46%로 뉴스/사설(1% 내외)보다 훨씬 높습니다. 법률 도메인은 원본 자체의 길이 분산이 매우 커서(표준편차 196.5, 최대 1,748 토큰 — `raw_length_full_stats.csv` 참고), target_length를 한 번 더 늘리는 것만으로는 완전히 해소되지 않는 근본적인 난이도가 있다는 뜻입니다. 코드에는 이 다음 시도로 target_length=200 재토큰화를 위한 스크립트(`train_step_fixed_comparison_law200.py` 등)를 준비했던 흔적이 남아 있으나, 실제로 별도의 target200 데이터셋을 재생성하지 않은 채 기존 target190 데이터셋을 그대로 참조하고 있어 — 이 저장소에는 완결되지 않은 실험이라 포함하지 않았습니다. 법률 도메인의 길이 문제는 "개선되었으나 완전히 해결되지는 않은" 상태로 남아 있습니다.

**평가 스크립트의 디버깅 흔적:** `evaluate_step_fixed_comparison.py`의 `calculate_nli_faithfulness` 함수에는 NLI 배치 전체가 패딩 없이 꽉 차면 transformers의 SDPA attention 최적화 경로에서 device-side CUDA assert가 발생하는 버그를 우회하기 위해, 항상 최소 32개의 패딩 토큰이 남도록 `truncation(480) + pad(max_length=512)`를 분리 적용한 부분이 있습니다. 원인 추적을 위해 `CUDA_LAUNCH_BLOCKING=1`로 동기 실행 모드를 켠 흔적도 코드에 그대로 남겨두었습니다.

## 저장소 구성

```
preprocess.py                          # AI Hub JSON -> 도메인별 정제 CSV
tokenize_data.py                       # 도메인별 토큰화 (target_length=128)
tokenize_law_target190.py              # 법률 도메인만 target_length=190 재토큰화
train.py                               # 1단계: 베이스라인 스케일업 학습 (15k~320k)
evaluate_a.py                          # 1단계: ROUGE+BERTScore+NLI 종합 평가
analyze_raw_length_full.py             # 진단1: 원본 요약 길이의 도메인별 구조적 차이 검증
check_generation_cap_ratio.py          # 진단2: 생성 시 EOS 없는 강제 캡 비율 검증
grid_search_generation.py              # 진단3: 생성 파라미터 그리드서치로 재학습 없이 해결 가능한지 검증
analyze_sample_size_length.py          # 진단4: 샘플링 편향 가능성 배제
train_step_fixed_comparison.py         # 3단계: 총 스텝 고정 재학습 (데이터량 vs 스텝 수 분리)
evaluate_step_fixed_comparison.py      # 3단계: 스텝 고정 모델 4종 종합 평가 및 최종 판정
```

원본 JSON 데이터셋, 생성된 대용량 CSV(최대 1.16GB), 학습된 모델 체크포인트(`final_kobart_summary_model_*`, `final_models_step_fixed*`), 중간 산출물 디렉토리(`tokenized_dataset_*`, `results_*`)는 용량 문제로 저장소에서 제외했습니다. T5 기반 토큰화(`tokenize_t5.py`)를 시도했던 흔적도 있으나, 최종적으로 KoBART 경로로 진행이 확정되어 이 저장소에는 포함하지 않았습니다.

## 사용 모델 / 지표

- 요약 모델: `digit82/kobart-summarization` (토크나이저: `gogamza/kobart-base-v2`)
- BERTScore: `klue/roberta-large` (`num_layers=17`)
- NLI 사실 부합도: `Huffon/klue-roberta-base-nli`의 entailment 확률을 원문-요약 사실 일치도의 proxy로 사용
- ROUGE: Mecab(또는 Kiwi) 형태소 분석기 기반 토큰화 후 채점
